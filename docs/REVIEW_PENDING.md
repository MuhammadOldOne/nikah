# Замечания проверки, которые ещё не исправлены

Это замечания независимой проверки интеграции со старым ботом (вторая сборка). Их нашли рецензенты, но **перепроверка (verify) и исправление не завершились**: облачная сессия закончилась раньше. Обзор UX/оформления не успел завершиться — его нужно провести заново.

Как работать с этим списком: по каждому пункту сначала убедиться, что проблема реальная (прочитать код, по возможности воспроизвести тестом), затем исправить по сути и добавить регрессионный тест. После всех исправлений прогнать полный набор тестов, e2e и `alembic check`. Выполненные пункты удалить из файла.

## migration (перенос и переключение)

### 1. [high] DEPLOY.md §9, a required preparation step, starts the new bot while the old one still runs; the widget also lets people create profiles before the import
- **Файл:** `docs/DEPLOY.md:275`
- **Проблема:** CUTOVER.md line 7 (§0) says the server must be prepared with DEPLOY.md sections 1–9 before the cutover. Section 9 (Telegram Login widget) tells the operator, at step 3, to run `docker compose up -d` ("контейнеры пересоздадутся"). Every compose combination includes `bot`: I checked all six COMPOSE_FILE variants with `docker compose config --services`, and `bot` has no profile in any of them. So this command starts the new bot with the production token while the old systemd bot is still running, which is exactly what §10 and CUTOVER step 1 forbid. The header comment of docker-compose.yml (line 2: "then: docker compose up -d --build") gives the same unsafe command. Separately, once TELEGRAM_WIDGET_ENABLED=true, the site at CUTOVER step 1 accepts logins through the widget (app/web/routes/auth.py `telegram_widget` does not need the bot process). This contradicts CUTOVER line 45 ("войти на него пока нельзя ... до переноса в новой базе не должно появиться ни одной анкеты").
- **Сценарий:** The owner follows CUTOVER §0 and does DEPLOY §9 a day before the cutover. `docker compose up -d` starts `bot`. Both bots poll getUpdates with one token and get 409 Conflict, so updates are split between them. Legacy users whose updates reach the new bot (empty DB) see the no-profile menu and the consent flow. Some press «Создать анкету» and finish, and the new bot also sets its own command menu. Even without the bot, any visitor can log in with the widget and create a profile on the site, which gets №500, the same number as the legacy №500. At CUTOVER step 5, after the old bot was already stopped and disabled at step 3, `--commit` refuses with «в новой базе уже есть данные (profiles: N)». The operator is stuck mid-cutover and must roll back or drop the DB, losing those users' new data.
- **Как исправить:** In DEPLOY §9 say the widget is enabled only after CUTOVER step 6. If it is done earlier, run `docker compose up -d web`, never a bare `up -d`. Add to CUTOVER §0 and step 1 that TELEGRAM_WIDGET_ENABLED must be false until the new bot is running, and that step 1 must not start `bot`. Change the docker-compose.yml header comment to point to DEPLOY/CUTOVER (`docker compose up -d db web [caddy]` before the import) instead of `docker compose up -d --build`.

### 2. [medium] Consent gate keeps only the last message sent before consent; earlier chat messages are silently dropped
- **Файл:** `app/bot/handlers/consent.py:68`
- **Проблема:** `ask()` stores the waiting action with `state.update_data({PENDING_KEY: pending})`, which overwrites the previous value. Every migrated user with a profile has consent_at NULL, so all of their chat texts go through this path until they press «Даю согласие». After consent, `on_give_consent` delivers only the one stored text. Each earlier message gets a consent prompt of its own and is then discarded without notice. The pending text also lives only in MemoryStorage, so a bot restart before consent loses it. CUTOVER.md lines 97 and 168 promise that messages written during the downtime are not lost and are processed after start. For migrated users in open chats, every one of those messages hits this gate.
- **Сценарий:** Reproduced with a scratch test using the tests/bot harness against my test DB. The migrated user (profile, consent_at NULL, open legacy chat) sends «Первое сообщение», «Второе сообщение», «Третье сообщение». They see three consent prompts, then press «Даю согласие». The messages table then holds only ['Третье сообщение']; the first two never reach the partner or the witness, and the sender is not told. In production this hits everyone who wrote to their partner during the cutover window: Telegram replays those queued messages at startup, all of them before consent.
- **Как исправить:** Keep a bounded, ordered list of pending texts (append, not overwrite) and deliver all of them in order after consent through chats.deliver. Show the prompt once, then use a short «сообщение будет отправлено после согласия» note. Store the pending list durably (DB or persistent FSM storage) so a restart does not drop it. Alternatively, tell the user explicitly that the message was not sent and must be repeated. Add a bot test with several messages before consent.

### 3. [low] Rollback leaves the site running, so site chat keeps accepting messages that never reach Telegram and are discarded by the retry
- **Файл:** `docs/CUTOVER.md:190`
- **Проблема:** The rollback section says «Сайт можно оставить работать или остановить». After rollback the old bot is live again on data.db, while people who logged into the site during the new-system period keep valid session cookies. On the site they can keep chatting in migrated conversations: chat.send_message writes to PostgreSQL and the outbox, but nothing delivers to Telegram (the new bot is stopped and the old bot reads only data.db). The documented «Повторная попытка» then requires DROP DATABASE, which deletes everything written on the site after the rollback.
- **Сценарий:** The cutover runs for an hour and some users log into the site. A proxy problem forces a rollback and the web container is left running as the doc allows. A sister keeps writing to her partner on /chats; the site shows the messages as sent, but her partner on the old Telegram bot never receives them. The next day the operator follows «Повторная попытка» (DROP/CREATE nikah plus a re-import from the old data.db), and those messages are lost for good.
- **Как исправить:** Make stopping the site part of the rollback: `docker compose stop bot web` (and `caddy` in Caddy mode), or switch the site into a maintenance page, before `systemctl enable --now <имя_сервиса>`. State that anything done in the new system after the rollback is not carried over.

### 4. [low] After rollback the new bot's command menu and reply keyboard remain, and the old bot relays their labels into chats
- **Файл:** `docs/CUTOVER.md:183`
- **Проблема:** At startup the new bot calls set_my_commands for all private chats (adds /stop, /delete) and per admin (app/bot/dispatcher.py set_commands). It also shows its own reply keyboard («Отклики», «Настройки», «Сайт»). The rollback steps only stop the new bot and start the old service. The old bot never calls set_my_commands and has no handler for these commands or labels, so its catch-all `relay_text` (legacy handlers/chat.py) forwards them as chat text to the partner and the witness.
- **Сценарий:** After a rollback, a user in an open chat taps /delete in the command menu, expecting their account to be deleted, or taps «Отклики» on the new keyboard still on screen. The old bot sends «Анкета №N пишет: /delete» (or «Отклики») to the partner and copies it to the witness group, and no deletion happens.
- **Как исправить:** Add a rollback step, run before starting the old service, that clears the new bot's commands: deleteMyCommands for BotCommandScopeAllPrivateChats and for each admin chat scope. For example, a small `docker compose run --rm --no-deps bot python -c ...` snippet or a `scripts/` helper. Also note in the rollback section that users should press /start in the old bot to get its keyboard back (admins and witnesses can announce this).

## parity (совпадение со старым ботом)

### 5. [high] Contact filter no longer hides an @username written straight after a word (the old bot did)
- **Файл:** `app/text.py:88`
- **Проблема:** The @username pattern starts with the lookbehind `(?<![\w@.])`. When '@' comes right after a letter, digit or underscore ("тг@ivanov_99", "inst@ivanov_99", "пиши@ivanov"), the pattern does not match. The e-mail pattern needs a dot and a TLD, so it does not catch these either. The old bot used `@[A-Za-z0-9_]{4,}` with no lookbehind and replaced all of these with [скрыто свидетелем]. hide_contacts (chat messages) and find_contacts (profile and interest texts) share this engine, so the gap exists in both channels and in profiles. Such a message is not flagged as 'contact-leak filter'. The sender gets no notice, the witness gets no flag, and the recipient sees the handle in clear.
- **Сценарий:** Reproduced in the scratchpad with contacts.py. hide_contacts('тг@ivanov_99') returns ('тг@ivanov_99', False), while the old filter gives ('тг[скрыто свидетелем]', True). The same holds for 'ник@ivanov_99', 'inst@ivanov_99', 'telegram@ivanov99', 'пиши@ivanov' and 'a@ivanov_99'. A brother in an open chat sends 'мой тг@ivan_1990'. The sister receives the handle unmasked, the message is not flagged, and the copy reaches the witness without any marker. A profile 'О себе' that contains 'inst@ivan_ov' also passes validation.
- **Как исправить:** Relax the lookbehind so that only '@' and '.' before the '@' are excluded, e.g. `(?<![@.])@\s?(?=[a-z0-9_.]*[a-z])[a-z0-9_][a-z0-9_.]{2,}`. Real e-mails are still matched by the e-mail pattern, and overlapping spans are merged into one placeholder, so nothing over-hides. Add the cases above to the text tests, plus a check that 'ivan@mail.ru' still becomes a single placeholder.

### 6. [medium] «Написать (заинтересоваться)» opens a dialog that takes the next chat message and sends it to another profile
- **Файл:** `app/bot/handlers/catalog.py:120`
- **Проблема:** In the old bot, br:int:<id> sent the interest at once (alert «Заявка отправлена»), and any later plain text went to the open chat. Now start_interest (called for the new card button and for the old br:int button in handlers/legacy.py:42) sets CatalogForm.interest_message. It then treats the next plain text as the interest message to the target profile. That dialog state is checked before the fallback relay. A person with one open chat who taps the button, does not notice the prompt and keeps chatting has their chat text sent as the interest message to a different person. Their partner never receives it. This conflicts with LEGACY_BOT.md §2.7 («любой текст уходит в него»), and the private text reaches a stranger.
- **Сценарий:** Reproduced (test_parity_c.py): man has an open chat with №501 and taps an old br:int:502 button. The bot asks «Напишите короткое сообщение к отклику…». He writes 'Как прошёл ваш день? Мои родители хотят познакомиться', meaning it for №501. The DB then holds interests(id=2, from man to №502, pending, message='Как прошёл ваш день? Мои родители хотят познакомиться'). The bot answers «Ваш отклик анкете №502 отправлен». No message was stored for the open chat. ReportForm.comment captures chat text the same way and makes it a report comment.
- **Как исправить:** Do not capture plain text for the optional interest message while the user has an open chat. Options: make the prompt a ForceReply and accept only a reply to it; or, when open_conversations() is non-empty, send the interest without a message at once (the old one-tap behaviour) and offer «Добавить сообщение» as an explicit button. At minimum, keep the old br:int callback one-tap, as it was.

### 7. [medium] Flood control in the witness group holds back every user's chat messages in Telegram
- **Файл:** `app/bot/outbox.py:67`
- **Проблема:** TelegramRetryAfter is in TELEGRAM_UNAVAILABLE. _send sleeps retry_after inline up to MAX_FLOOD_RETRIES times and then re-raises. process_batch then stops at that row and the worker pauses for OUTAGE_PAUSE (5 s, growing to 300 s). Every chat message adds a witness.copy row for the one WITNESS_CHAT_ID group, and Telegram caps a group at about 20 bot messages per minute. Once traffic across all chats goes above that, the group's per-chat flood limit is handled like a global outage. All rows behind it wait: partner messages, interests, moderation results. The old bot sent to the partner first and only logged a failed witness copy, so chatting never slowed down.
- **Сценарий:** Reproduced (test_parity_d.py, FakeBot). The group returns RetryAfter(1) four times. The woman sends «Салам», then the man answers «Ва алейкум салам». One process_batch ran for 3.0 s and delivered the woman's message to the man. The man's reply was not delivered to the woman, and the worker paused (telegram_unavailable=True). In production retry_after is often tens of seconds, and the pause doubles up to 5 minutes while the group stays limited. Then all Telegram relays fall minutes behind once the platform passes about 20 messages per minute in total.
- **Как исправить:** Treat RetryAfter from the witness chat as a per-chat condition, not an outage. Reschedule only that row (next_attempt_at = now + retry_after, no attempt counted) and continue the batch, while still keeping per-recipient ordering (skip later rows to the same chat_id in this batch). Alternatively, run witness deliveries in a separate lane or worker, so participant messages are never queued behind group copies.

### 8. [medium] «Дополнить анкету» invites a typed number of children, but the typed answer goes to the chat partner
- **Файл:** `app/bot/handlers/profile.py:301`
- **Проблема:** ask_missing uses QUESTIONS['children'] = «Сколько у вас детей? Выберите или напишите число.», but the completion flow has no state: it only handles FillCb button presses (0–5). A typed answer therefore lands in the fallback relay_text. With one open chat, the number goes to the partner as a chat message. Without one, the user gets «Сейчас у вас нет открытого чата…». Someone with 6 or more children cannot answer at all. This affects every migrated profile, because all of them lack the field.
- **Сценарий:** Reproduced (test_parity_e.py): a migrated man with an open chat sends /start and taps «Дополнить анкету (1 минута)». He answers marital status by button, then gets the children question and types '7'. The result: Message('7') is stored and relayed to his partner as «Анкета №N пишет: 7», and profile.children stays None.
- **Как исправить:** Use a completion-specific question without «или напишите число» and add a «6 и больше» button (or a small FSM state for this one numeric step that accepts digits). Do not reuse the wizard QUESTIONS text in ask_missing.

### 9. [low] A Telegram Reply to the old bot's «Чат открыт…» or «Мой чат» message is refused instead of relayed
- **Файл:** `app/bot/handlers/chats.py:237`
- **Проблема:** The old intro «Чат открыт между анкетами №A и №B… Просто пишите сюда текстом» and the old «Мой чат» answer «Открыт чат с анкетой №N. Пишите сюда — бот передаст.» both carry the old button chat:close. _reply_target cannot read 'chat:close' as ChatCb, which needs a conversation_id, so it finds no target. _misdirected_reply then sees a bot message with a keyboard and returns REPLY_NOT_TO_CHAT. The old bot relayed such replies to the open chat. People with chats migrated open still have these messages on screen, and the messages themselves tell them to write here.
- **Сценарий:** Reproduced (test_parity_a.py): man with one open chat uses Telegram «Reply» on a bot message whose keyboard is [[Завершить общение → chat:close]] and writes 'Ассаляму алейкум!'. The bot answers «Это сообщение не из чата, поэтому ответ никуда не отправлен…», and no Message is stored. The same happens for a Reply to the old «Мой чат» status message.
- **Как исправить:** In _misdirected_reply (or _reply_target), treat a keyboard whose only callback is LEGACY_CHAT_CLOSE as belonging to 'the only open chat'. Return None there so deliver() sends the text to the only open chat, just as the old bot did.

### 10. [low] Repeating an interest asks for a message first and refuses only after the person has typed it
- **Файл:** `app/bot/handlers/catalog.py:113`
- **Проблема:** start_interest only checks require_active(own profile) and then opens the message prompt. It does not check the pair rules in send_interest: a pending interest or open chat (InterestAlreadyExists), an earlier interest that was declined or accepted, a witness block, or the daily limit. The old bot answered br:int at once with the alert «Вы уже отправляли заявку на эту анкету.». Now the person writes a message and then gets the refusal, and the text is lost.
- **Сценарий:** Reproduced (test_parity_b.py): man has already sent an interest to №501 and taps «Написать (заинтересоваться)» or the old br:int:501 again. The bot shows «Напишите короткое сообщение к отклику…». After he types a message, it answers «Между вами уже есть отклик или переписка.». The same happens once INTEREST_DAILY_LIMIT is reached.
- **Как исправить:** Add a read-only service check, e.g. interests.check_can_send(session, user, to_user_id), that raises the same domain errors as send_interest without writing. Call it in start_interest and answer the callback with exc.message (show_alert) before opening the dialog. The site profile page and the p_<number> button logic can reuse it, which also covers the known 'may send after a closed chat' gap.

### 11. [low] /ban, /unban and /admin in the witness group are silently ignored (the old bot handled them)
- **Файл:** `app/bot/middlewares.py:120`
- **Проблема:** UserMiddleware passes group updates only to the witness router, so admin commands sent in WITNESS_CHAT_ID get no handler and no reply. The old admin router had no chat-type filter: /ban <id> and /unban <id> from an admin in the witness group worked and answered «Пользователь … заблокирован.». The new copies in the group read «Чат #5 | №512 → №513», and /ban №512 is now the documented syntax, so admins will naturally type it there. Nothing happens and nothing is said.
- **Сценарий:** Reproduced (test_parity_b.py): with WITNESS_CHAT_ID=GROUP and ADMIN_TELEGRAM_IDS=[ADMIN_TG], the admin sends '/ban <telegram_id>', '/ban №500' and '/admin' in the group. The bot makes no API request, and the user stays unbanned (is_banned=False).
- **Как исправить:** Let /ban and /unban through in the witness group for admins: register them in the root witness router, or let UserMiddleware route admin commands there. Their replies hold only «Анкета №N», which is safe for the group. For /admin in the group, reply with a short hint to use it in the private chat, so profile cards are not posted to the group and the command is still not silently dropped.

## rules (правила и конкурентность)

### 12. [medium] A witness-closed pair can open a new chat by accepting a leftover crossed pending interest
- **Файл:** `app/services/interests.py:197`
- **Проблема:** `send_interest` refuses a pair that has a conversation closed by the witness (`InterestBlockedByWitness`). `accept()` has no such check, and `witness.witness_close` does not cancel the pair's pending interests. The import deliberately keeps the legacy state where both directions are pending. The legacy `decide_interest` left the reverse interest pending after an accept, so a legacy pair can have an open chat plus a pending interest the other way. Once the witness closes that chat, the remaining interest can still be accepted from /interests, from the bot's «Отклики», or from the old `int:acc:<id>` button still on the person's screen. That opens a new chat at once and undoes the witness's decision, contradicting MVP §4, decision 18 and the `witness_close` docstring.
- **Сценарий:** Reproduced with test_witness_close_is_undone_by_accepting_the_crossed_interest in /tmp/claude-0/-home-user-nikah/23d9128e-b8c4-5c00-bef6-c1e3d720bb44/scratchpad/review/test_review_rules.py. The legacy pair has interests A→B and B→A, both pending. B accepts A→B and the chat opens. The witness presses «🚫 Закрыть чат» and the chat closes with closed_by_witness. A then presses the old «Принять» (int:acc:<B→A id>). `interests.accept` succeeds and returns a new open conversation for the pair.
- **Как исправить:** In `accept()`, run the same `closed_by_witness` exists-check as `send_interest` after the users rows are locked, and raise `InterestBlockedByWitness`. Also have `witness_close` (or `force_close` with CLOSED_BY_WITNESS) set the pair's pending interests in both directions to cancelled, so the stale cards disappear from /interests and the bot. Add a test using crossed pending interests.

### 13. [medium] Consent gate replays a Telegram «Reply» into the wrong chat after «Даю согласие»
- **Файл:** `app/bot/handlers/consent.py:140`
- **Проблема:** For a migrated user without consent, `ConsentGate` stores only `event.text` as the pending action (line 118). `on_give_consent` then calls `chats.deliver(callback, session, user, pending)` with no conversation_id, so the text goes to the only open chat or the active one. Everything the normal relay checks is skipped. The reply target from `_reply_target`, which may be a closed chat or a different chat, is lost. So is the `_misdirected_reply` refusal for replies to interest or profile cards and wali copies (decision 16). Every migrated user hits this gate on their first message after cutover, while old legacy messages with `rep:`/`int:acc` buttons are still on their screens.
- **Сценарий:** Reproduced with test_consent_gate_delivers_a_misdirected_reply_to_another_chat in /tmp/claude-0/-home-user-nikah/23d9128e-b8c4-5c00-bef6-c1e3d720bb44/scratchpad/review/test_review_bot.py. Migrated user A has a closed chat with B and an open chat with C. A uses Telegram «Reply» on an old relayed message from B and writes «Ответ для B». With consent, this reply would be refused because B's chat is closed. Here the consent prompt appears, A presses «Даю согласие», and «Ответ для B» is stored in the chat with C and relayed to C (and to C's wali and the witness).
- **Как исправить:** When storing the pending action, resolve it the way `relay_text` does. For a reply, store the resolved conversation_id, or store nothing and ask the person to send the text again after consent. Never carry over a reply that `_misdirected_reply` would refuse. In `on_give_consent`, pass the stored conversation_id to `deliver`.

### 14. [low] Closing a chat takes no row lock: concurrent closes both succeed and the last writer's close_reason wins
- **Файл:** `app/services/chat.py:342`
- **Проблема:** `close_conversation` (site and bot) and `witness_close` check `conversation.is_open` on an object read without a lock: `get_conversation_for_participant`, or `session.get` in witness.py:89. `force_close` then runs a plain UPDATE by primary key. Two closes that overlap both pass the check. Under READ COMMITTED the second UPDATE waits, then overwrites closed_at, closed_by_id and close_reason, and both emit `conversation.closed` and `witness.conversation_closed`. `SimpleEventIsolation` only serializes one Telegram user in one chat. It does not cover two admins in the witness group, the site and the bot together, or two site requests.
- **Сценарий:** Reproduced with test_concurrent_witness_and_user_close and test_double_tap_close in /tmp/claude-0/-home-user-nikah/23d9128e-b8c4-5c00-bef6-c1e3d720bb44/scratchpad/review/test_review_rules.py. The witness presses «🚫 Закрыть чат» while the woman presses «Завершить общение» on the site. Both calls succeed, the final close_reason is closed_by_user, and there are 2 conversation.closed and 2 witness.conversation_closed rows. Because the stored reason is no longer closed_by_witness, `send_interest`'s InterestBlockedByWitness check no longer blocks the pair. The participants get both «Свидетель завершил ваш чат» and «Анкета №N завершила общение», and the witness group gets two notices. Two admins pressing the button together, or a site double-submit, give duplicate notifications in the same way.
- **Как исправить:** In `force_close`, after the users UPDATE (to keep the lock order), re-read the conversation with `with_for_update={"key_share": True}, populate_existing=True`. Alternatively use `UPDATE conversations ... WHERE id = :id AND closed_at IS NULL RETURNING id`. If it is already closed, raise `ConversationClosed` (callers already handle it) or skip without emitting. `ban` and `delete_account` should skip instead of raising.

### 15. [low] Bot profile edit saves the whole snapshot draft, reverting fields changed elsewhere meanwhile
- **Файл:** `app/bot/handlers/profile.py:632`
- **Проблема:** `start_editing` snapshots every field into `wizard.draft` (line 353), and the bot asks for one field. `_save_changes` sends the whole draft through `ProfileUpdate.from_form(draft, current_profile)`. Any field that differs from the current stored value counts as a change, including values the person changed on the site, or with the bot's one-tap «Дополнить анкету», after the snapshot was taken. Optional fields are silently set back to the old value. Free-text fields are set back too, which sends the profile back to moderation: with PREMODERATION on, the person can no longer browse or send interests. Required fields filled meanwhile are cleared, which fails validation and loses the bot edit. The draft lives in MemoryStorage until the bot restarts, so the «Сохранить» button of an abandoned edit keeps working.
- **Сценарий:** Reproduced with test_bot_edit_reverts_changes_made_on_the_site_meanwhile in /tmp/claude-0/-home-user-nikah/23d9128e-b8c4-5c00-bef6-c1e3d720bb44/scratchpad/review/test_review_bot.py. The user starts «Редактировать» in the bot and picks «Город». Meanwhile, on the site, they set height 165 and a new «О себе». They type «Москва» in the bot and press «Сохранить». The stored profile then has city Москва, height NULL and the old «О себе», with status pending: the site edits are lost and the profile is re-moderated.
- **Как исправить:** Track the fields the wizard actually changed: a `touched` set, or a diff against the snapshot taken at `start_editing`. Pass only those to `ProfileUpdate.from_form` in `_save_changes`. The same stale-form problem exists for the site's full `/me/edit` form, which could post only the fields that differ from the values rendered into it (e.g. hidden originals).

### 16. [low] Witness group upgraded to a supergroup: every witness notice is retried 8 times and dropped, with no fallback to admins
- **Файл:** `app/bot/outbox.py:446`

### 17. [low] Account deletion racing an accept leaves the partner an open chat with a deleted account
- **Файл:** `app/services/users.py:191`

### 18. [medium] Contact filter misses mixed-script homoglyphs, invisible non-Cf characters and short-link TLDs (interest messages carry them with no witness copy)

The same input with a Latin 'a' is rejected with InvalidInput. Interest messages get no witness.copy, so this is a channel where contacts reach a sister with no witness oversight at all.
- **Сценарий:** A brother sends an interest with the message «пишите мне @ivаnov_99 или 8ㅤ912ㅤ345ㅤ67ㅤ89» (Cyrillic 'а'; U+3164 between the digit groups). send_interest accepts it, unflagged, and the sister reads '@ivanov_99' and '8 912 345 67 89'. In chats, 'linktr.ee/ivanov', 't.mе/ivanov' (Cyrillic 'е') and '@iv͏anov_99' are stored and relayed as is, with no CONTACTS_HIDDEN_NOTICE and no 'contact-leak filter' flag for the moderators.
- **Как исправить:** In `_folded`, also apply a confusables fold for matching only: map Cyrillic/Greek look-alikes (а→a, е→e, о→o, р→p, с→c, у→y, х→x, к→k, м→m, т→t, і→i, ѕ→s, ј→j, ԁ→d…) to Latin, so the @username, t.me and Latin-domain patterns see 'ivanov' and 't.me'. Spans already map back to the original characters. In `_strip_controls`, also drop Mn/Me characters that are not attached to a preceding letter that needs them (at least U+034F, U+17B4/U+17B5, U+180B–U+180F, U+FE00–U+FE0F outside emoji), and Hangul fillers and U+2800, or treat them as separators in `_SEPARATORS`. Add a generic 'host.tld/path' rule (Latin label, dot, 2–6 Latin letters, then '/'), which rarely fires on Russian prose and catches linktr.ee/, goo.gl/, is.gd/, rb.gy/, lnk.bio/, beacons.ai/.
