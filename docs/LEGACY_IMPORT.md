# Перенос пользователей и анкет из текущего бота

Сейчас @nikah_istina_bot работает на старом сервере (`oldvps`) со своей базой. Новая система
использует тот же токен и переносит людей по `telegram_id`, поэтому для пользователей бот остаётся
прежним. Схема старой базы пока неизвестна, поэтому перенос делается в два этапа:

1. владелец снимает со старой базы **только схему** (таблицы, колонки, типы, количество строк) и
   присылает её разработчику;
2. разработчик пишет по схеме маппинг в `scripts/import_legacy.py`, и владелец запускает перенос
   **на сервере**.

Сами данные никогда не покидают серверы и не попадают в репозиторий.

## Почему данные нельзя класть в репозиторий

- **Репозиторий публичный.** Любой файл в нём может скачать кто угодно, в том числе боты, которые
  сканируют GitHub в поисках утечек.
- **Git помнит всё.** Удалённый файл остаётся в истории коммитов и в форках. «Удалить потом» уже
  не получится.
- **Это особая категория персональных данных.** Анкеты никах-сервиса раскрывают религиозные убеждения
  (152-ФЗ, ст. 10), а ещё имена, города, семейное положение, Telegram ID и переписку. Утечка — это
  штрафы, а главное — реальный риск для людей, особенно для сестёр.

Поэтому в репозиторий, issues, чаты и письма **нельзя** отправлять: файлы баз (`*.db`, `*.sqlite`),
дампы и резервные копии, CSV/JSON-выгрузки, скриншоты с анкетами, логи с данными пользователей,
`.env` и токены. Отправлять можно **только** вывод `--inspect`: в нём нет содержимого строк.

## Шаг 1. Найти базу старого бота

На `oldvps` посмотрите, как бот хранит данные. Обычно это файл SQLite рядом с кодом или база PostgreSQL:

```bash
ps aux | grep -i python                         # путь к скрипту бота → его папка
ls -la /путь/к/боту                             # файлы *.db, *.sqlite, *.sqlite3
grep -rn -i -E "sqlite|\.db\b|postgres|database_url" /путь/к/боту \
  --include=*.py --include=*.env --include=*.json --include=*.ini --include=*.toml | grep -v venv
sudo -u postgres psql -l 2>/dev/null             # базы PostgreSQL, если он установлен
```

Последняя `grep` может показать пароль от базы или токен: не копируйте этот вывод никуда.

Если данные хранятся иначе (MySQL, JSON-файлы, Redis, Google-таблица), напишите разработчику,
**что** это за хранилище. Сами файлы не присылайте.

## Шаг 2. Снять схему (`--inspect`)

`--inspect` открывает базу **только для чтения** и печатает только таблицы, колонки, типы, ключи и
количество строк. Содержимое строк он не выводит никогда. Старый бот при этом может продолжать работать.

Скопируйте скрипт на старый сервер, например с нового:

```bash
scp /opt/nikah/scripts/import_legacy.py root@oldvps:/root/import_legacy.py
```

**SQLite.** Нужен только Python 3.8+ без дополнительных пакетов:

```bash
python3 /root/import_legacy.py --inspect /путь/к/боту/bot.db > /root/legacy-schema.txt
cat /root/legacy-schema.txt
```

**PostgreSQL.** Нужен пакет `asyncpg`. Он ставится во временное окружение; если `venv` не создаётся,
сначала выполните `apt install -y python3-venv`.

```bash
python3 -m venv /tmp/inspect && /tmp/inspect/bin/pip install asyncpg
/tmp/inspect/bin/python /root/import_legacy.py \
  --inspect 'postgresql://ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ@127.0.0.1:5432/ИМЯ_БАЗЫ' > /root/legacy-schema.txt
rm -rf /tmp/inspect
```

Пример вывода:

```
Источник: SQLite
Таблиц: 2
Показаны только структура и количество строк. Содержимое строк не выводится.

Таблица users (строк: 1342)
  id           INTEGER  PK
  telegram_id  INTEGER  NOT NULL
  name         TEXT
  ...
```

Перед отправкой **просмотрите файл глазами**. Если в названиях таблиц или колонок встречаются
Telegram ID, имена или телефоны (некоторые боты создают таблицу на каждого пользователя), замените
их на `***`. Затем отправьте разработчику только `legacy-schema.txt`.

Если разработчику нужен код старого бота, сначала уберите из него токен, пароли и файлы с данными.

Пока старый бот работает, сделайте резервную копию его базы. Она **остаётся на сервере**:

```bash
# SQLite: целостная копия одним файлом, даже если бот работает
python3 -c "import sqlite3; s = sqlite3.connect('/путь/к/боту/bot.db'); d = sqlite3.connect('/root/legacy-backup.db'); s.backup(d); d.close()"
# PostgreSQL
pg_dump -Fc --no-owner --no-acl 'postgresql://ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ@127.0.0.1:5432/ИМЯ_БАЗЫ' > /root/legacy-backup.dump
chmod 600 /root/legacy-backup.*
```

## Шаг 3. Маппинг (делает разработчик)

По присланной схеме разработчик заполняет раздел `MAPPING` в `scripts/import_legacy.py`: функция
`read_legacy_records` читает строки старой базы и превращает каждого человека в `LegacyRecord`.
Это Telegram ID, имя и username из Telegram, время согласия и поля анкеты в словаре новой системы
(`app/enums.py`, `app/schemas.py`). Пока раздел не заполнен, `--import` завершается сообщением
«Заполните маппинг после --inspect».

Решения, которые нужны от владельца и юриста:

- **Согласие.** Распространяется ли согласие, данное в старом боте, на новый сервис? Если да,
  маппинг передаёт время согласия, и человек переносится вместе с анкетой. Если нет или согласия не
  было, человек **не переносится**: при следующем `/start` бот попросит новое согласие, и анкету нужно
  будет заполнить заново.
- **Модерация.** Перенесённые анкеты попадают в очередь `/admin/moderation`, как новые
  (при `PREMODERATION=false` публикуются сразу). Уведомления при переносе не рассылаются.

Как ведёт себя импорт:

- аккаунты, которые уже есть в новой базе (тот же Telegram ID), не изменяются, поэтому повторный
  запуск безопасен;
- анкеты проверяются по тем же правилам, что и новые: 18+, без контактов в тексте, допустимые
  значения. Не прошедшие проверку анкеты не переносятся. В отчёте видно только, какие поля не прошли
  и сколько раз, без значений;
- тексты со стоп-словами помечаются для модератора.

## Шаг 4. Пробный прогон на новом сервере

Переносить нужно **финальные** данные, поэтому сначала остановите старый бот
([DEPLOY.md](DEPLOY.md), шаг 7). Затем перенесите копию базы на новый сервер в папку **вне
репозитория**. Код в контейнере работает от пользователя с UID 10001, поэтому файл отдаётся ему:

```bash
# на oldvps — целостная копия (SQLite)
python3 -c "import sqlite3; s = sqlite3.connect('/путь/к/боту/bot.db'); d = sqlite3.connect('/root/legacy-export.db'); s.backup(d); d.close()"

# на новом сервере
install -d -m 700 /opt/legacy
scp root@oldvps:/root/legacy-export.db /opt/legacy/bot.db
chown 10001:10001 /opt/legacy/bot.db && chmod 600 /opt/legacy/bot.db
```

Поднимите базу новой системы и создайте схему (сайт и бот пока не запускаются):

```bash
cd /opt/nikah
docker compose up -d db
docker compose run --rm web alembic upgrade head
```

Пробный прогон: всё проверяется и откатывается, в базу ничего не записывается.

```bash
docker compose run --rm -v /opt/legacy/bot.db:/legacy/bot.db:ro web \
  python -m scripts.import_legacy --import /legacy/bot.db
```

**Если старая база — PostgreSQL**, восстановите её дамп во временную базу внутри нового стека и
импортируйте оттуда:

```bash
scp root@oldvps:/root/legacy-backup.dump /opt/legacy/legacy.dump
docker compose exec db createdb -U nikah legacy
docker compose exec -T db pg_restore -U nikah -d legacy --no-owner --no-acl < /opt/legacy/legacy.dump
docker compose run --rm web sh -c \
  'python -m scripts.import_legacy --import "postgresql://nikah:$POSTGRES_PASSWORD@db:5432/legacy"'
```

Проверьте отчёт: сколько людей и анкет будет перенесено, сколько пропущено и почему.

## Шаг 5. Перенос и уборка

Та же команда с `--commit` записывает данные:

```bash
docker compose run --rm -v /opt/legacy/bot.db:/legacy/bot.db:ro web \
  python -m scripts.import_legacy --import /legacy/bot.db --commit
```

Дальше:

1. Запустите систему: `docker compose up -d --build` ([DEPLOY.md](DEPLOY.md), шаги 9–10).
2. Одобрите перенесённые анкеты в https://ДОМЕН/admin/moderation.
3. Удалите временные копии с нового сервера: `rm -rf /opt/legacy`. Для PostgreSQL также
   `docker compose exec db dropdb -U nikah legacy`.
4. Резервная копия на `oldvps` (шаг 2) хранится, пока новая система не проработает спокойно
   оговорённый срок. Потом удалите её вместе со старой базой: хранить персональные данные дольше
   необходимого нельзя.
